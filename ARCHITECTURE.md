## 1. Цели и принципы

**Продуктовые цели:**
- 3D-сцена с редактированием: создание примитивов, импорт OBJ/FBX, ручной ввод Scale, перемещение/вращение/масштаб гизмо.
- Управление симуляцией: пауза/пуск/пошаговый кадр, глобальная гравитация, плотность воздуха.
- Пер-объектное включение/выключение физики (Rigidbody) без пересоздания объекта.
- База из 100+ материалов и сплавов: выбор материала меняет визуал (цвет, металличность, шероховатость, текстуры) и физику (масса = ρ·V, трение, упругость, аэродинамическое сопротивление).
- Экспорт/импорт сцены и объектов (OBJ + JSON-сцена).

**Инженерные принципы (отсюда растёт вся архитектура):**

| # | Принцип | Что это даёт |
|---|---------|--------------|
| P1 | **Модульность через Assembly Definitions** — один модуль = одна asmdef = один слой ответственности | Компиляция по частям, невозможность «случайных» зависимостей, быстрый CI |
| P2 | **Домен не знает про UI**. Домен публикует события (`EventBus`), UI подписывается | UI можно переписать/отключить, не трогая симуляцию |
| P3 | **Никаких статических синглтонов**. Единственная точка композиции — `AppBootstrap` + `ServiceRegistry` | Явный порядок инициализации, тестируемость |
| P4 | **Данные отдельно от логики**: материалы — ScriptableObject-ассеты, сцена — JSON-DTO | Дизайнеры пополняют базу материалов без кода, сейвы версионируются |
| P5 | **Всё расширяемое — за интерфейсами**: `IModelImporter`, `IFileDialogService`, `ICommand` | OBJ/FBX/ glTF — это плагины к ядру, а не «зашитый» код |
| P6 | **Каждое действие пользователя = команда** (`ICommand`) | Undo/Redo почти бесплатно и консистентно |

## 2. Технологические решения

| Вопрос | Решение | Обоснование | Альтернатива (и почему нет) |
|--------|---------|-------------|------------------------------|
| Версия Unity | **2022.3 LTS** (или Unity 6 — код совместим) | Стабильность, долгая поддержка, зрелый UI Toolkit | Unity 6 обязателен только ради `linearVelocity` — не критично |
| Рендер | **URP + Shader Graph** (`URP/Lit`) | Качественный PBR (metallic/smoothness), GPU instancing, пост-эффекты | HDRP тяжёлый; Built-in — устаревший PBR |
| Физика | **Built-in PhysX** (`UnityEngine.Physics`) | Много цел, сочленения, стабильный солвер; наша аэродинамика — это силы поверх него | DOTS Physics избыточен, интероп сложнее |
| UI | **UI Toolkit (runtime)** | ListView легко держит 100+ материалов с поиском/фильтром, стили как CSS, UXML раскладка | uGUI — больше ручной работы для «редакторских» панелей |
| Пауза симуляции | **`Physics.simulationMode = Script`**, шаг — `Physics.Simulate(dt)` | Честный покадровый шаг; не трогаем `Time.timeScale` → анимации UI/камера живут при паузе | `Time.timeScale = 0` замораживает всё и не даёт шага |
| DI | **Лёгкий самописный `ServiceRegistry`** (~50 строк) + ручная композиция в `AppBootstrap` | Полный контроль, ноль зависимостей, порядок инициализации очевиден | Zenject/VContainer — перебор для 8 сервисов |
| Локализация | Русский язык UI, код и идентификаторы — английские | Строки UI в одном месте (`UiStrings`), легко добавить таблицу локализации позже | — |
| Целевая платформа | Windows/Mac/Linux Standalone + редактор | Нативные диалоги файлов, FBX-плагин | WebGL — нет нативных диалогов/FBX, вне скоупа v1 |

**Производственные ориентиры:** 60 FPS при 500–1000 активных тел (PhysX с solverIterations ≈ 8), нулевые аллокации в `FixedUpdate`, объём/масса пересчитываются только при изменении геометрии.

### 2.1 Уточнения при реализации (v1.1 — финальные решения)

В ходе сплошной реализации приняты следующие уточнения к таблице выше (все — в сторону надёжности «открыл и работает»):

- **Рендер:** Built-in RP + шейдер `Standard`. URP из проекта убран; `MaterialApplier` поддерживает оба шейдера (URP/Lit подхватится автоматически, если проект переведут на URP).
- **UI:** uGUI, собирается целиком кодом (нулевые ассеты — ничего не сломается при импорте). UI Toolkit — будущий апгрейд, панели изолированы за `UIRoot`.
- **Ввод:** стандартный Input Manager (пакет Input System убран — меньше зависимостей, работает из коробки).
- **Сцена:** `Main.unity` содержит единственный объект `AppBootstrap`; вся сцена (камера, свет, земля, UI, сервисы) собирается кодом при старте — нет хрупких YAML-зависимостей.
- **Материалы:** встроенная таблица 121 материала в коде (`MaterialSpecs`) — работает в рантайме без единого ассета; опционально editor-импортёр CSV создаёт SO-ассеты для дизайнерскогоworkflow.
- **FBX:** заглушка с честным сообщением в UI (нужен нативный плагин AssimpNet, путь подключения описан в README). OBJ-путь (свой парсер) реализован полностью.
- **`IFileDialogService`** — асинхронный (колбэк): в редакторе нативные диалоги, в билде — встроенный модальный диалог ввода пути.

## 3. Модульная карта (asmdef) и правила зависимостей

Восемь сборок. Стрелка = «ссылается на» (asmdef reference). Запрещены циклы.

```text
                        ┌───────────────────────────┐
                        │         UI (Toolkit)      │  ← единственный, кто видит почти всех
                        └─────┬────┬────┬────┬──────┘
                              │    │    │    │
        ┌───────────────┐   ┌─┴──┐ │  ┌─┴────┴─────┐
        │  Interaction  │   │Sim.│ │  │ ImportExport│
        │ камера/выбор/ │   └─┬──┘ │  └─┬───┬───┬───┘
        │  гизмо        │     │    │    │   │   │
        └───────┬───────┘     ▼    ▼    ▼   │   │
                │        ┌──────────┐  ┌──▼───┴───▼───┐
                │        │Materials │  │  Geometry     │
                │        │ БД 100+  │  │ фабрика +     │
                │        │материалов│  │ объём меша    │
                │        └────┬─────┘  └──────┬────────┘
                │             │               │
                ▼             ▼               ▼
        ┌─────────────────────────────────────────────┐
        │                   Core                      │
        │  SceneObject, WorldRegistry, EventBus,      │
        │  ServiceRegistry, CommandStack, события     │
        └─────────────────────────────────────────────┘
                        ▲
        ┌───────────────┴────────────────┐
        │   App (composition root)       │ ← зависит от всех, его не зависит никто
        │   AppBootstrap                 │
        └────────────────────────────────┘
```

| Сборка | Ссылается на | Ответственность |
|--------|--------------|-----------------|
| `PhysSim.Core` | — | Домен: модель объекта, реестр сцены, события, DI-контейнер, undo-стек, контракты сервисов |
| `PhysSim.Simulation` | Core | Управление временем/гравитацией, тело с физикой + аэродинамика |
| `PhysSim.Materials` | Core, Simulation | База материалов (SO), применение материала к объекту (визуал + физика) |
| `PhysSim.Geometry` | Core, Simulation, Materials | Фабрика примитивов/мешей, вычисление объёма меша |
| `PhysSim.ImportExport` | Core, Geometry, Materials | Импортёры OBJ/FBX, экспортёр OBJ, сериализация сцены |
| `PhysSim.Interaction` | Core | Камера, выбор объектов, гизмо трансформаций |
| `PhysSim.UI` | Core, Simulation, Materials, Geometry, ImportExport, Interaction | Панели UI Toolkit, диалоги файлов (реализация `IFileDialogService`) |
| `PhysSim.App` | все | `AppBootstrap` — композиция и порядок инициализации |

**Железные правила:**
1. Никто не ссылается на `UI` и `App`, кроме `App` → `UI`.
2. Модули общаются **только** через `EventBus` и реестры из `Core` — прямых ссылок «сосед на соседа» в логике нет (кроме легальных: `Materials → SimulatedBody`, `Geometry → фабрика тел`).
3. Каждая asmdef имеет свой `rootNamespace`: `PhysSim.<Module>`.

## 5. Компонентная модель объекта сцены

Каждый объект на сцене — один `GameObject` со стандартным «компонентным комплектом». Логика размазана по маленьким компонентам, а не в одном god-object:

```text
SceneObject (root)                     ← Core: идентификатор, имя, ссылки (Rigidbody, Collider, Renderer)
├── MeshFilter / MeshRenderer          ← Unity (или SkinnedMeshRenderer после FBX)
├── Collider  (Box/Sphere/Capsule/Mesh)← Unity; MeshCollider с convex=true для физики
├── Rigidbody                          ← Unity; создаётся ВСЕГДА, isKinematic=true (физика выключена)
├── SimulatedBody                      ← Simulation: вкл/выкл физики, объём, масса=ρV, аэродинамика (FixedUpdate)
└── MaterialAssignment                 ← Materials: текущий MaterialDefinition объекта
```

**Почему Rigidbody всегда:** переключение физики — это `isKinematic = true/false`, мгновенно и без пересоздания коллайдеров. Выключенная физика = кинематика: объект неподвижен, но другие тела об него ударяются (поведение «стены») — так и ждём от редактора.

**Цепочка пересчётов** (важный инвариант):

```text
Создание / Импорт / Смена Scale / Смена меша
        → MeshVolumeCalculator.Calculate(mesh)        (Geometry)
        → SimulatedBody.SetVolume(V)                  (Simulation)
        → RecalculateMass(density материала)          (Simulation)
        → Rigidbody.mass = ρ · V                      (PhysX)
```

Масса никогда не хранится «сама по себе» — она всегда производная от объёма и плотности материала (плюс опциональный `massOverride`).

## 8. Система материалов: база 100+ материалов

### 8.1 Схема `MaterialDefinition`

```csharp
id              string   — стабильный ключ ("iron", "paper_office"), никогда не меняется
displayName     string   — русское имя ("Железо")
category        enum     — Metal | Alloy | Wood | Paper | Plastic | Rubber | Glass |
                           Ceramic | Stone | Fabric | Organic | Composite | Other
density         float    — кг/м³ (железо 7870, бумага ~800–1000, пробка 240)
staticFriction  float    — 0..1.5
dynamicFriction float    — 0..1.5
restitution     float    — 0..1 (резина 0.85, глина 0)
dragCoefficient float    — базовый Cd материала, «парусность» (бумага 1.8, шар металла ~0.5–1.0)
color           Color    — линейный цвет albedo
metallic        float    — 0..1 (URP)
smoothness      float    — 0..1 (аналог шероховатости, invRoughness)
albedoMap       Texture2D? / normalMap / maskMap (URP), tiling
```

Единственный источник правды о материале — ассет `MaterialDefinition`. Визуал и физика — два следствия одного ассета, применяются атомарно методом `MaterialApplier.Apply()`.

### 8.2 Пайплайн наполнения базы

```text
materials.csv  ──(Editor: MaterialCsvImporter, M3)──►  Assets/_Project/Data/Materials/*.asset
(120 строк,                                                    │
 правится в любом редакторе)                                   ▼
                                                    MaterialDatabase.asset
                                                    (индекс + валидация уникальности id)
```

CSV позволяет держать 120+ материалов как данные: плотности/трения берём из справочников, стартовые значения лежат в репозитории и тюнятся правкой одной таблицы. В рантайме база тоже расширяется (`MaterialDatabase.Register`) — например, пользовательский материал.

## 9. Физическая модель: масса и аэродинамика

### 9.1 Масса

```text
m = ρ_материала · V_меша        V — по теореме о расходимости (замкнутый меш)
Rigidbody.mass = m               при massOverride — override, но в UI показываем и расчётную
```

### 9.2 Аэродинамика (каждый FixedUpdate, только когда физика включена)

```text
F_drag = ½ · ρ_воздуха · Cd · A · |v|²      направление: против вектора скорости
A      — площадь сечения по AABB объекта (v1: максимальная грань; v2 — проекция по направлению v)
Cd     — из MaterialDefinition (парусность материала), интегрируется с формой
a      = F_drag / m   ← вот почему бумага падает медленно: у неё малые m и большой Cd
```

Никакого «читерского» drag через `Rigidbody.drag` — только честная сила `AddForce`, поэтому формула прозрачна и тестируема.

### 9.3 Проверка на числа (куб 25 см, A = 0.0625 м², g = 9.81)

Терминальная скорость: `v_t = √(2·m·g / (ρ_возд·Cd·A))`

| Материал | ρ, кг/м³ | Масса, кг | Cd | v_t, м/с |
|----------|---------:|----------:|---:|---------:|
| Бумага, **лист** 250×250×1 мм | 900 | 0.056 | 1.8 | **≈ 2.8** |
| Бумага, куб 25 см | 900 | 14.1 | 1.8 | ≈ 45 |
| Дуб, куб | 750 | 11.7 | 1.0 | ≈ 55 |
| Алюминий, куб | 2700 | 42.2 | 0.9 | ≈ 110 |
| Железо, куб | 7870 | 123 | 0.9 | **≈ 187** |
| Золото, куб | 19300 | 302 | 0.9 | ≈ 293 |

(Это предел падения с большой высоты, а не результат 3-метрового сброса — но разница «бумага/железо» видна уже с 2–3 метров.) Дополнительно каждый объект с включённой физикой показывает расчётную `v_t` в инспекторе — удобная проверка, что материал применился.

### 9.4 Настройки солвера

- `Time.fixedDeltaTime = 0.02` (50 Гц), `Physics.defaultSolverIterations = 8`, `solverVelocityIterations = 2` — устойчивые стопки из сотен тел.
- CCD для мелких быстрых объектов (ключ `SimSettings`).
- `PhysicMaterial.combine = Average`; вопрос комбинирования трения двух материалов — кандидат на отдельную настройку в M5.
- Вакуум-демо: слайдер ρ воздуха в 0 → все тела падают одинаково. Отличная проверка корректности модели.

## 10. Импорт / экспорт

### 10.1 Модели

- **OBJ — реализуем сами** (парсер ~300 строк, полный контроль, без нативных зависимостей): полигоны fan-треугольниками, группы → отдельные `SceneObject`, RH→LH (флип X), `mtl` опционально.
- **FBX — через AssimpNet** (нативный плагин, Standalone+Editor). FBX-специфика (версии, см, RH) остаётся внутри `FbxImporter`; наружу — тот же `IModelImporter`. Это единственный внешний «жирный» компонент, и он спрятан за интерфейсом: если плагин не подошёл, добавим `GlTfImporter` и не тронем ни строчки в других модулях.

### 10.2 Сцена (сохранение/загрузка)

```json
{
  "version": 1,
  "savedAt": "2026-09-24T12:00:00Z",
  "gravity": 9.80665,
  "airDensity": 1.225,
  "timeScale": 1.0,
  "objects": [
    {
      "id": "0f8fad5b…",
      "name": "Куб 1",
      "primitive": "Cube",
      "position": [0, 2.5, 0], "rotation": [0, 0, 0], "scale": [1, 1, 1],
      "materialId": "iron",
      "physicsEnabled": false,
      "massOverride": null
    },
    {
      "id": "9b2cf535…",
      "name": "Деталь от заказчика",
```

## 12. История действий (Undo/Redo)

Каждая мутирующая операция оборачивается в `ICommand` и попадает в `CommandStack`:

`SpawnObjectCommand`, `DeleteObjectCommand`, `TransformObjectCommand`, `SetMaterialCommand`, `TogglePhysicsCommand`, `RenameObjectCommand`, `ImportObjectsCommand` (композит), `SetGravityCommand`.

Правило: команды оперируют идентификаторами и маленькими снапшотами (TRS, materialId) — не держат ссылок на тяжёлые объекты. Удаление объекта физически отложенное (ObjectDestroyer), пока команда в стеке.

## 13. Инициализация приложения (Bootstrap)

`AppBootstrap` (единственная сцена `Main.unity`) собирает мир в строгом порядке:

```text
1. Core        ServiceRegistry, EventBus, WorldRegistry, CommandStack
2. Данные      MaterialDatabase (ассет), SimSettings
3. Simulation  SimulationManager (старт в паузе!), SimulatedBody — компонентный, внедряется фабрикой
4. Materials   MaterialApplier
5. Geometry    ObjectFactory (получает реестр, шину, менеджер симуляции, базу, аплаер)
6. ImportExport ObjImporter, FbxImporter, ObjExporter, SceneSerializer (+ IFileDialogService из UI на M4)
7. Interaction CameraRig, SelectionManager, TransformGizmoService
8. UI          UIRoot — последним: подписывается на события, читает реестры
9. Стартап     Пустая сцена ИЛИ восстановление последней (PlayerPrefs: путь) — настройка
```

Приложение **всегда стартует на паузе** — это редактор, а не игра. Пользователь сам запускает физику.

## 17. Риски и их снятие

| Риск | Вероятность | Снятие |
|------|-------------|--------|
| FBX в рантайме — самый сложный формат | высокая | FBX только через AssimpNet за `IModelImporter`; OBJ — наш, гарантирован; glTF — запасной маршрут |
| Незамкнутые меши из интернета → объём врёт | высокая | `CalculateOrEstimate` с fallback «bounds × заполнение» + предупреждение в UI |
| «Бумага-куб» падает быстро, пользователь ждёт «как лист» | средняя | Логика физически честна (см. §9.3); в UI подсказка: форма влияет, создавайте лист-масштаб; Cd материала усиливает эффект |
| Тормоза при 1000+ тел | средняя | 50 Гц физики, итерации солвера по бюджету, нулевые аллокации в FixedUpdate, GPU instancing, опция «спать дальние тела» |
| Драг-энд-дроп файлов в окно | низкая | v1 — диалоги файлов; drag&drop — в бэклоге M6 (Application.openFile hook) |

## 18. Конвенции кода

- Имена: классы/методы — английские, `PascalCase`; XML-doc комментарии — русские (команда русскоязычная).
- Один публичный класс — один файл, имя файла = имя класса.
- `readonly struct` для идентификаторов/событий; `I`-префикс интерфейсов; суффиксы `Dto`, `Panel`, `Service`, `Manager` — по роли.
- Без LINQ и аллокаций в `FixedUpdate`/`Update`; кешировать компоненты в `Awake`.
- Доступ к чужим модулям — через `ServiceRegistry`/`EventBus`, не через `FindObjectOfType` (запрещён вне bootstrap).
- Магические константы физики — только в `SimSettings`/`MaterialDefinition`, не в коде.
- Каждая веха = серия маленьких коммитов; коммит не ломает компиляцию.
